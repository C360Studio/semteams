# Coordination design admission

This is a documentation decision for [#335](https://github.com/C360Studio/semteams/issues/335), claimed by [PR #358](https://github.com/C360Studio/semteams/pull/358). [ADR-064](../../../../docs/adr/064-rule-pack-coordination-and-source-observation.md) records the durable reasons. This change admits one narrow later implementation proof and defines the boundaries that later multi-manager work must satisfy. It changes no runtime behavior.

## Current evidence and boundary

The running shell uses frozen SemStreams. Live category packs are `research` and `autoresearch`; the development packs are parked. The product-owned `github_read` reads allowlisted GitHub repositories and deduplicates by per-repository/kind cursor and per-origin version digest. Its `RunCursorStore` returns the pre-run baseline on retries and stages updates until a downstream research artifact commits the run ([cursor.go:26-66](../../../../cmd/semteams/tools/githubread/cursor.go), [executor.go:386-461](../../../../cmd/semteams/tools/githubread/executor.go), [emitartifact/executor.go:409-419](../../../../cmd/semteams/tools/emitartifact/executor.go)). Production calls omit `ListOpts.Since` and fetch one newest-first page per kind, capped at 1–100 requested items (default 20; issues may request extra rows to exclude PRs), without following pagination ([executor.go:282-287](../../../../cmd/semteams/tools/githubread/executor.go), [executor.go:832-855](../../../../cmd/semteams/tools/githubread/executor.go), [client.go:221-266](../../../../cmd/semteams/tools/githubread/client.go)). That bounded window cannot prove exhaustive catch-up or identify every older missing change. A future watcher must qualify this seam before reusing it; merely invoking `github_read` on a timer does not provide a durable source-to-task boundary.

SemTeams will own agent-specific loop, dispatch, context, governance, trajectories and rule extensions after independently qualified extraction. SemEngine owns generic transport, graph, mutation, rule, lifecycle/projection and durability. This change chooses no graph inbox, KV bucket, stream, queue, API or claim mechanism. It does not treat [SemEngine #24](https://github.com/C360Studio/semengine/issues/24) as a blanket hold on agent-runtime extraction; it also does not infer generic effect/replay guarantees from current cursor or graph state.

## Source observation and pack policy

A proposed service-side source adapter inspects source changes and emits validated observations with stable source object and revision identity, explicit configured program/project scope, provenance, retrieval time, and freshness state. Category rule packs decide whether an observation warrants a bounded task; this adapter's poll tick alone does not invoke a model. The current opt-in scheduled Program Pulse separately uses cron to publish a coordinator task ([10-scheduled-program-pulse.json:1-24](../../../../configs/rules/research/10-scheduled-program-pulse.json)); this design does not migrate that journey. GitHub/Gitea artifacts remain authoritative for repository discussion and work; a source observation is a typed input to policy, not an instruction or approval. Non-forge teams can later use adapters for timers, documents or incoming messages through the same policy boundary.

Outbound polling is a supported target mode without a public inbound receiver. A configured webhook may accelerate detection, but only reconciliation against the source can produce an accepted observation. Today `/work` uses its own SvelteKit server GitHub source, separate from `github_read` ([service.ts:80-108](../../../../ui/src/lib/server/work/service.ts), [executor.go:23-28](../../../../cmd/semteams/tools/githubread/executor.go)); a shared adapter is a target, and `/work` migration needs a separate observable-work change. Later provider slices must state signal coverage, incremental query and pagination behavior, checkpoint timing, overlap deduplication, rate-limit/outage handling, freshness, and gaps such as intermediate events or deletions that polling cannot reconstruct. Gitea requires separate qualification. SemSource can enrich code/document evidence via supported interfaces when indexing is useful; it is not part of the first forge observation proof.

## First implementation candidate

One configured GitHub repository contains one existing issue. The proof stages a discovered source delta, persists the downstream observation/result through a selected proven boundary, then commits the cursor. An unchanged poll is suppressed only after that commit. The future claim must specify how it qualifies this boundary, including restart behavior, before promising duplicate suppression across interruption.

| Input or step | Required first-proof outcome |
| --- | --- |
| Baseline, then issue fixture title/body and `updated_at` change | A source read discovers and stages one logical observation with stable issue/revision identity and configured program/project scope. |
| Persisted observation/result, then cursor commit, then unchanged poll | The post-commit poll emits no new observation for that revision. A staged cursor alone is insufficient. |
| Retry before the downstream commit | The same source identity may be returned again; no once-execution or outside-effect claim follows. |
| Repository or project outside explicit configuration | Refuse the observation; never guess a scope from recent activity. |
| Failed or incomplete fetch, including an incomplete page | Keep the last successful cursor and surface unavailable/partial state; do not report an empty successful result. The current single-page window cannot prove exhaustive catch-up or detect every unseen older item; detecting an incomplete page and proving this refusal criterion need qualification before reuse. Full multi-page coverage remains a later slice. |
| Prompt-like issue body and synthetic credential fixture | Treat prose as untrusted data and redact the synthetic secret before any persisted observation/result. No model invocation is required to prove the boundary. |

This proof needs no runtime task response, SemSource, inbound endpoint, or Gitea adapter. It establishes source observation and its declared commit boundary only, not durable dispatch or exactly-once external effects.

Follow-up slices may test complete pagination, rate-limit recovery, wider outage/freshness behavior, webhook overlap, additional forge signals, and non-forge events. Those are acceptance needs for the broader target, not behavior delivered by this docs-only change or the first issue fixture.

## Multi-manager admission boundary

Before activating delegated Project Managers, a request design must validate explicit sender and recipient program/project coordinates against operator configuration, name the originating run and evidence references, and reject unknown or ambiently inferred scope. It must bound pending work, attempts, fan-out, time and expenditure across the run; a per-loop ceiling alone does not cap concurrent work. [#301](https://github.com/C360Studio/semteams/issues/301) owns cost accounting/policy, [#298](https://github.com/C360Studio/semteams/issues/298) reactive policy, [#299](https://github.com/C360Studio/semteams/issues/299) external effects, and [#333](https://github.com/C360Studio/semteams/issues/333) delegated authority. A policy threshold observed after spending is not a strict concurrent admission cap. The design must state which component checks admission and how unknown usage, retries, cancellation and in-flight overshoot are represented.

A possible `pending → claimed → completed | cancelled` request is a lifecycle candidate, not a selected storage implementation. A future slice must qualify one successful claimant, cancellation/refusal, visible uncertain outcomes and recovery against implemented substrate contracts. Neither accepted transport delivery nor a successful graph transition is proof of an outside effect.

Cross-project bodies and external repository prose are untrusted. A manager receives bounded metadata and authenticated sender coordinates first, then explicitly retrieves the body inside an escaped untrusted-input fence. Verified principal/delegate and source provenance remain outside that fence. Typed `[REDACTED:<kind>]` markers are applied before persisting cross-project payloads, tool outputs or trajectories. Tests in the implementation slice must show refusal of inferred scope, prompt-like source text failing to acquire control authority, and secret-class identification without retained secret values.

## Decision boundaries

GitHub issues own later implementation sequencing and holds. An implementation claim selects exact fixture and affected source path, names its commit boundary, and supplies independent regression evidence. It must pass framework-alignment review before adding any new tool, payload, rule action, KV bucket or stream. This design does not activate parked packs, change the read-only Program Pulse authority, adopt a frontier harness, or reopen subscription-backed CLI execution.
