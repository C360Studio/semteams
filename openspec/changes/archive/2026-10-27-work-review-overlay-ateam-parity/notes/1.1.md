# Task notes: verdict state, lane keys, and comment pagination

## Verdict state for non-exact `APPROVE` (task 1.1)

ATeam `internal/review/gate.go` `gateVerdict()` (`36b999b`, lines 823-840) approves only when the trimmed line starts
with `Verdict:` and the whole remaining value equals `APPROVE`. A `current` overlay must mean that gate would approve,
so every other value led by `APPROVE` (`pending`, `once`, `until`, `after`, `if`, `, but REQUEST CHANGES`, `with nits`,
`(0 BLOCKING, 1 NIT)`, `` `APPROVE` ``, `**Verdict**:` emphasis, `APPROVED`, `PASS`) is left unparsed rather than mapped
to `changes_requested`. This applies to ATeam-format records only: historical `<!-- semteams-review-record -->` marker
records keep their `verdict:` field mapping, where `pass` and `approved` still map to `pass`. Both are fail-closed; `unknown` was chosen because the comment's intent is unreadable, not a
recorded request for changes, and it keeps one rule for every non-gate approval. Values led by `REQUEST CHANGES`,
`CHANGES REQUESTED`, `BLOCKING`, or `FAIL` still map to `blocking` through the existing clause split: they can never
report a false approval. More than one `Verdict:` line (even two identical `APPROVE` lines) is unparsed, matching
`gateVerdict()`'s "has N Verdict: lines".

The approval check reads the original comment body, never the text after `stripKeywordInlineCode`. That filter exists
for reviewer-identity and `Reviewed at <sha>` recognition and deletes inline code mentioning `verdict`, so running the
check on it let ``Verdict: APPROVE `pending verdict tests` `` read as `current` (cross-agent review H1 on `e56105a9`).
Lines come from a port of ATeam `unfencedLines()` (`internal/review/aiprecord.go` `36b999b`, lines 98-123: split on
`\n`, drop a trailing `\r`, a fence opens on any run of three or more `` ` `` or `~` indented at most three spaces and
closes on a same-character run at least as long with nothing after it) and are trimmed like Go `strings.TrimSpace`
(`unicode.IsSpace`, which includes U+0085 and U+00A0 but not U+FEFF, unlike JavaScript `trim()`). A `pass` also
requires the parser's own lenient scan to see exactly one `Verdict:` line, so where the two fence rules disagree the
result is never more permissive than ATeam's gate. The lenient scan's leading indent accepts the same Unicode spaces,
so a lone `\u00a0Verdict: APPROVE` approves as it does in ATeam.

## Lane keys (tasks 1.2 and 2.1)

A lane value's keys are its `<name>-reviewer` tokens (`go-reviewer, svelte-reviewer (cross-agent)` covers both). Lane
text with no such token is one opaque key, so `Lane: ui` never clears `svelte-reviewer`. A record with no lane line is
an all-lanes record.

Every valid record is replayed in comment order at any SHA (ATeam `record()` keeps the latest valid record whatever
commit it names); an earlier draft replayed only records at `HEAD`, which let a later `REQUEST CHANGES` at an older SHA
be skipped in favour of an earlier `APPROVE` at `HEAD`. From the surviving per-lane state: the newest blocking record
wins, else the newest record not at `HEAD` (stale), else the latest record. A valid all-lanes `REQUEST CHANGES` stays
effective after every named lane approves until a newer all-lanes record; that is deliberate and fail-closed.

An unparseable comment is cleared against the surviving lane state: one naming lanes needs every lane held by a newer
record; one with a reviewer identity (`reviewed-by:` or the cross-agent heading) but no lane would have been an
all-lanes record, so it needs a newer all-lanes record; one with neither (the #365 implementer-reply case) is cleared by
any newer record.

## Pagination over fail-closed (task 2.2)

`getGithubJson` already reads one page per call, so paginating is a loop over `&page=N` and stops at the first short
page. That is smaller than fail-closed handling and keeps the overlay `known` on long PR threads. The loop is capped at
`MAX_PR_COMMENT_PAGES` (10, i.e. 1,000 comments) to bound reads per refresh across up to `MAX_OPEN_PR_COMMENT_FETCHES`
PRs; when the last page read is still full, a newer record could sit beyond it, so the PR fails closed to
`review_inspected: false`. The earlier exception that kept a truncated page `inspected` when its record matched `HEAD`
is removed, because that is the #366 page-2 `REQUEST CHANGES` case.

Limits: pages are read sequentially, so one PR costs at most `MAX_PR_COMMENT_PAGES` x `READ_TIMEOUT_MS` in the worst
case. Page-number pagination over ascending comments is not snapshot-consistent: a comment added between page reads
lands on a later page and is still read, but a comment deleted between reads shifts the next page and can skip one
comment.
