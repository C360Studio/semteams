# Task notes: verdict state, lane keys, and comment pagination

## Verdict state for non-exact `APPROVE` (task 1.1)

ATeam `internal/review/gate.go` `gateVerdict()` (`36b999b`, lines 823-840) approves only when the trimmed line starts
with `Verdict:` and the whole remaining value equals `APPROVE`. A `current` overlay must mean that gate would approve,
so every other value led by `APPROVE` (`pending`, `once`, `until`, `after`, `if`, `, but REQUEST CHANGES`, `with nits`,
`(0 BLOCKING, 1 NIT)`, `` `APPROVE` ``, `**Verdict**:` emphasis, `APPROVED`, `PASS`) is left unparsed rather than mapped
to `changes_requested`. Both are fail-closed; `unknown` was chosen because the comment's intent is unreadable, not a
recorded request for changes, and it keeps one rule for every non-gate approval. Values led by `REQUEST CHANGES`,
`CHANGES REQUESTED`, `BLOCKING`, or `FAIL` still map to `blocking` through the existing clause split: they can never
report a false approval. More than one `Verdict:` line (even two identical `APPROVE` lines) is unparsed, matching
`gateVerdict()`'s "has N Verdict: lines".

## Lane keys (tasks 1.2 and 2.1)

A lane value's keys are its `<name>-reviewer` tokens (`go-reviewer, svelte-reviewer (cross-agent)` covers both). Lane
text with no such token is one opaque key, so `Lane: ui` never clears `svelte-reviewer`. A record with no lane line is
an all-lanes record. An unparseable comment with no lane line is cleared by any later valid record (ATeam `record()`
behavior and the #365 implementer-reply case); one naming lanes is cleared only by a later record covering all of them.

## Pagination over fail-closed (task 2.2)

`getGithubJson` already reads one page per call, so paginating is a loop over `&page=N` and stops at the first short
page. That is smaller than fail-closed handling and keeps the overlay `known` on long PR threads. The loop is capped at
`MAX_PR_COMMENT_PAGES` (10, i.e. 1,000 comments) to bound reads per refresh across up to `MAX_OPEN_PR_COMMENT_FETCHES`
PRs; when the last page read is still full, a newer record could sit beyond it, so the PR fails closed to
`review_inspected: false`. The earlier exception that kept a truncated page `inspected` when its record matched `HEAD`
is removed, because that is the #366 page-2 `REQUEST CHANGES` case.
